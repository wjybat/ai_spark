# 海外商机与客户情报 Agent 项目技术报告

> 报告日期：2026-09-10  
> 代码基线：`04b49d3`（最近提交日期 2026-09-07）  
> 范围：当前仓库内三个业务后端及一个展示前端，以实际源码、配置、测试结果为依据。  
> 验证方式：静态代码检查、离线自动化测试、TypeScript 检查。未进行真实模型调用、生产构建、浏览器端到端测试或压力测试。

## 一、执行摘要

项目面向海外市场拓展、战略研究和客户经营，包含三个业务环节：

1. **市场雷达**：研究目标国家与零售商，以证据支撑市场指标、机会评分及优先级。
2. **海外商机决策**：生成国家管理层简报和客户 BD 作战包，覆盖画像、机会、能力匹配、风险与开发邮件。
3. **客户情报中心**：持续接入客户材料，沉淀事件、事实、客户阶段、经验和下一步行动。

当前技术路线是 **TypeScript 全栈 + 受限工具 Agent + 结构化证据 + 确定性业务规则 + SQLite**。它并非单一聊天应用，也不是已经统一的多智能体平台，而是多个可独立运行的 MVP 应用组合。

**综合判断：已形成可演示、可开展受控内部试用的工程基础，但尚不具备直接面向公网、多租户或高并发生产环境的完整条件。**

主要优势：

- 市场评分与语言模型分离，可解释、可重复计算。
- 多个业务页面支持结论到来源的追溯。
- Agent 通过业务工具工作，核心会话不开放通用 Shell、文件写入等能力。
- 长耗时任务与 Web 请求分离，市场研究具备租约、心跳、取消及任务事件。
- 本次离线验证共 **40 个测试文件、229 项测试全部通过**，三个后端的类型检查全部通过。

主要缺口：

- 三个业务应用尚未统一客户身份、权限和数据移交。
- 商机运行记录及生成报告保存在内存，服务重启即丢失。
- 未发现完整的统一鉴权、多租户隔离和 API 限流实现。
- 市场证据允许低精度自动核验；`verified` 不等于逐条经过人工审核。
- 生产运维、备份恢复、端到端测试及模型质量评估尚不完整。

### 架构特点

1. **前后端同语言**：TypeScript 降低类型和数据结构转换成本。
2. **模型与程序分工**：模型负责抽取和文字综合，程序负责状态变更、指标归一化、评分与结果校验。
3. **受限 Agent**：研究、客户抽取、客户问答分别创建受限会话，权限按任务区分。
4. **轻量持久化**：两套业务 SQLite 降低 MVP 部署成本，但共享文件和单写者约束不适合直接扩展为多节点写入。
5. **市场雷达分层更完整**：采用 `domain/contracts/application/infrastructure/agent/apps` 分层，并提供依赖边界检查；另外两个后端采用更紧凑的模块组织。

## 五、核心技术实现

### 5.1 客户情报中心：材料到客户状态

#### 处理链路

```text
文本 / PDF / DOCX / Markdown / TXT / 结构化事件
    → API 输入校验与客户匹配
    → SourceItem + ProcessingJob
    → Worker 原子领取任务
    → Pi Agent 读取当前客户和本次材料
    → 结构化提交 Event / Fact / Next Action
    → 确定性规则补充抽取与原文定位
    → 短事务写入
    → 重算客户状态、总结及经验
    → 前端轮询任务并刷新工作台
```

#### 关键机制

- **客户接入边界**：材料默认必须属于已有客户；只有显式 `auto_create_customer: true` 才允许自动创建。
- **来源幂等**：使用 `(source_system, external_id)` 唯一约束及内容哈希，相同内容重复接入不创建重复任务；内容变更会触发重新分析。
- **事实更新**：相同客户、事实类型、事实键的新值替换当前有效标记，保留其他历史事实记录。对同一来源重新分析时会删除并重建该来源的抽取结果，因此并非全量不可变事件溯源模型。
- **状态计算**：通过标准事件映射到 TARGET、POC、CONTRACT、DEPLOYMENT、PRODUCTION、EXPANSION 等阶段，再计算客户分类及 ACTIVE、WON、LOST、STALLED 等状态。
- **工作队列**：SQLite `BEGIN IMMEDIATE` 事务领取任务，默认约 1 秒空闲轮询。失败任务按尝试次数自动重试，终态失败支持人工重新分析。Worker 启动时恢复超过 10 分钟的处理任务。
- **结果通知**：浏览器约每 1.5 秒轮询任务状态，不是服务端 SSE。
- **数据库**：SQLite WAL、外键、5 秒 busy timeout，模型调用不持有数据库事务。
- **文件能力**：默认上传限制 30 MB；扫描 PDF 不支持 OCR。

#### Agent 权限

抽取 Agent 仅可读取当前客户画像、当前来源、有效事实及时间线，并调用终止工具 `submit_customer_analysis`。数据库写入由应用代码完成。

客户问答使用独立只读会话，可查询客户上下文、事实、时间线和材料。读取来源时校验客户归属，但这只是工具层数据范围约束，不能替代 HTTP 用户鉴权。

#### 数据模型

| 数据实体 | 职责 |
|---|---|
| `customers` / `customer_aliases` | 客户主数据与名称归一化 |
| `source_items` | 原始材料、来源标识、内容哈希与状态 |
| `processing_jobs` | 异步任务、尝试次数、错误及时间 |
| `customer_events` | 业务事件与发生时间 |
| `customer_facts` | 事实类型、键值、置信度、原文与当前标记 |
| `customer_summaries` | 当前状态、需求、阻碍、经验与行动聚合 |
| `customer_experiences` | 成功、失败及可复用方法 |

#### 重要边界

- 总结与经验由抽取结果加确定性规则聚合，不应宣传为全部由模型独立撰写。
- Pi 失败可按配置回退兼容模型或本地规则；即使 Pi 成功，也会合并部分启发式抽取结果。
- 原文定位优先使用精确子串；无法精确匹配时，采用字符二元组重合度寻找段落，最低阈值为 0.08。因此“能高亮某段原文”并不证明该段充分支持结论。
- 分析读取的单份来源最多 50,000 字符，事实/历史上下文也有数量上限，长文和长期客户需要后续分块与分层摘要方案。

### 5.2 市场雷达：研究、核验、指标与评分

#### 处理链路

```text
Scenario Revision（区域、国家、业态、时间窗、配置版本）
    → Research Plan（按国家与主题拆分）
    → Research Jobs（独立租约与并发执行）
    → Pi 搜索/网页提取 或 Fixture
    → Source Document / Snapshot
    → Evidence Candidate
    → 程序校验与 Verified Claim
    → Metric Engine
    → Scoring Engine
    → Country Score / Ranking / Explanation
```

#### 数据和工程约束

- 场景修订固定国家范围、研究时间窗及指标/参考集/评分模型版本。
- 使用带前缀 ID、UTC 毫秒、canonical JSON 与 SHA-256 哈希支持记录追溯和去重。
- 百分比、评分、权重、覆盖率及 EQI 使用 `0..10000` basis points 保存，避免显示精度与存储精度混淆。
- Fixture 与 Pi 研究按来源隔离，Pi 评分不消费 Fixture 证据。
- 研究 Worker 具备租约令牌、心跳、过期回收、取消轮询及尝试记录；默认并发配置为 3。
- 对话 Agent 查询持久化的排名、指标和证据，不自行搜索并改变正式评分。

#### 评分方法

六个维度为：

1. 市场规模 `market_size`
2. 增长 `growth`
3. 扩张 `expansion`
4. 数字化 `digital`
5. 客户价值 `customer_value`
6. 进入便利度 `entry_ease`

可用指标经版本化规则归一化后，维度分按可用指标权重重新归一化：

```text
维度覆盖率 = 可用指标权重之和 / 该维度指标总权重
维度分 = Σ(可用指标权重 × 指标归一化分) / Σ可用指标权重
机会分 = Σ(可用维度权重 × 维度分) / Σ可用维度权重
进入难度 = 100 − 进入便利度
```

覆盖率不足时返回缺失/不足状态，不将缺失值静默填成 0。Hard Blocker 优先于均分判断。

仓库内 `market-opportunity.1.2.0.json` 的门槛包括：

- 维度展示覆盖率至少 20%。
- 国家整体覆盖率至少 60%。
- 市场规模、客户价值、进入便利度分别至少 60%。
- P1 还要求机会分至少 80、进入难度不高于 65、覆盖率至少 80%、EQI 至少 70%。

这些是**版本化配置口径**，不是所有历史扫描共同使用的常量；实际运行应读取对应场景和评分版本。

#### 派生指标

引擎可从合格证据派生门店基数、零售商数量、增长率、客户价值、集中度和扩张信号等。部分指标属于代理估算，例如客户数量乘以预设 ACV 中点、伙伴供给映射销售摩擦等。

派生值可追溯输入 Claim 和计算版本，但不能将代理指标等同于公开统计原值、真实合同价格或成交预测。

#### 核验策略必须准确披露

当前研究策略偏向高召回：

- 谓词、值/单位/日期格式、URL、引用精确匹配、时间窗、零售商身份及数值依据等硬性失败阻止正式使用。
- 部分国家范围、年份语义、业态口径、法规分类及冲突问题作为警告保留。
- 带此类警告的证据可能自动成为 `verified` Claim，标记 `verification_method=auto_low_precision`，来源质量上限 40%。
- 确定性门槛通过后，使用低精度证据的国家仍可能发布结果，不强制全部进入人工审核。

因此，报告和 UI 应同时展示验证方式、低精度警告、覆盖率、EQI、数据时点与版本。**`verified` 仅代表通过当前管线规则，不代表人工核实或语义必然正确。**

此外，当前精确引用校验主要证明引文属于提交的来源摘录，应进一步强化“搜索/抓取实际响应 → 不可变快照 → 引文位置”的可信绑定，避免把模型提交的摘录本身视为最终真实性保证。

### 5.3 商机决策：九阶段客户作战包与国家综合

#### 客户作战包

单个 Pi Agent 按九阶段工具链执行：

```text
市场扫描 → 客户池 → 客户画像 → 商机信号 → 客户准入
    → 证据链 → 能力匹配 → 风险评估 → 研究 Brief
```

- 前置阶段主要依赖固定知识库及确定性分析。
- Live 模式第 7 阶段由模型撰写能力匹配参数，第 9 阶段由模型撰写英文开发邮件。
- 后端校验能力 ID、证据归属、分数范围和邮件格式。
- 校验失败可在同阶段修正；连续失败有上限，不能静默用模板冒充 Live 成果。
- Demo 使用真实 Agent 循环与工具调用，但 provider 是脚本化模拟，能力匹配与邮件采用规则/模板，并非真实模型在线推理。

市场雷达的正式评分与这里的能力匹配分属于不同体系。后者在 Live 模式可由模型给出、程序做范围与证据约束，不应套用“所有分数均由确定性引擎计算”的宣传口径。

#### 国家管理层简报

国家与客户流程独立：

- 服务端根据国家选择三家企业的完整资料。
- 首轮请求预加载国家及三家企业证据，避免多轮调用仅用于读取已知资料。
- 模型输出优先级、机会逻辑、企业判断、信号、风险、行动和置信度。
- 失败时通过 `repair_country_brief` 只修改指定顶层字段；合并后仍重新校验整篇结果。
- 未通过校验的草稿不发布，重新运行失败不覆盖上次成功内容。
- 前端与后端结果均非长期持久存储，页面刷新或服务重启会影响结果保留。

#### RAG 的实际形态

`src/rag/evidence-retriever.ts` 实现的是：

- 固定结构化证据集合；
- 按客户、区域和分类过滤；
- 关键词匹配分 + 来源等级 + 置信度排序；
- 同分时结合发布日期排序。

目前没有向量数据库、Embedding 检索、大规模自动增量索引或运行时通用网页爬取。这是轻量证据检索增强，而非完整企业级向量 RAG 平台。

#### 展示前端

D3/TopoJSON 提供地球和行政区划展示，国别资料与地图资源多数以本地脚本/JSON 组织。顶部“重新扫描市场”是纯前端演示，不等同于调用独立市场雷达的真实研究任务。

Markdown 渲染使用本地打包的 Marked 与 DOMPurify，过滤危险 HTML/链接；React、D3、TopoJSON、Babel 和字体仍有外部 CDN 依赖。

```text
review_status / reviewer / reviewed_at
```

建议由销售确认后触发移交，将外部研究事实与已确认客户互动区分存储，避免一份研究简报直接推动客户签约阶段或覆盖 CRM 事实。

## 八、性能、可观察性与部署

### 8.1 已有性能设计

- 模型与网络调用不长期占用客户数据库事务。
- 市场研究按主题拆分任务，支持并发与取消。
- 国家简报预加载证据、缩短输出、按字段修复，减少模型往返和整篇重生成。
- 客户详情读取持久化事实/总结，市场页面读取已保存指标和评分，避免每次打开页面重新调用模型。

### 8.2 历史性能记录，不是本次实测

依据 `global-opportunity-agent/docs/country-brief-performance.md`：

| 样本 | 历史结果 |
|---|---|
| 旧版加拿大流程 | 多轮读取、生成及整篇修复，240 秒超时失败 |
| 预加载后的早期较长文本版本 | 加拿大约 136.9 秒成功 |
| 精简后的加拿大两次 | 约 57.0 / 61.4 秒，一轮成功 |
| 修订接口完善后的巴西 | 约 65.5 秒，一轮成功 |

这些只是少量样本，不能推导稳定 P95、平均成本、所有国家的一分钟 SLA 或真实高并发能力。

### 8.3 可观察性现状

市场雷达具备请求/Trace ID、结构化日志、任务/尝试记录、扫描事件和 `/api/metrics`；国家简报记录模型轮次、耗时和校验失败，客户 Worker 主要使用控制台日志。

需注意市场管线 `aiRuns` 的部分提取记录仍按字符数估算 Token，且写入固定的延迟值；不能直接作为真实模型用量与计费依据。应统一采集 provider 实际 usage、请求耗时、重试次数和失败原因。

### 8.4 当前部署形态

- 客户中心：Web 默认 3001 端口，独立 Worker，共享 SQLite 和文件目录。
- 市场雷达：Web 默认 3000 端口，独立研究 Worker，共享市场 SQLite。
- 商机演示：Fastify 默认 8787 端口，同时托管静态展示前端。
- 项目中未发现完整 Docker/容器编排或 CI 工作流配置。

近期建议采用单机内网部署、进程守护、反向代理和受控访问。SQLite 应位于可靠本地持久卷，不应直接假设多个容器在共享网络文件系统上安全并发写入。

当出现多节点写入、严格审计或容量要求后，再迁移 PostgreSQL、对象存储及持久任务队列；无需为 MVP 提前引入复杂微服务。

## 九、风险评估与改进建议

| 优先级 | 风险/缺口 | 依据与影响 | 建议 |
|---|---|---|---|
| P0 | 统一鉴权和数据权限缺失 | 主要 API 未见用户认证链路；客户数据和模型调用存在暴露风险 | 公网开放前实现 SSO、资源归属、RBAC、审计与限流 |
| P0 | 商机状态未持久化 | RunStore 为内存 Map，无保留期限/容量策略 | 持久化运行、事件与报告；增加 TTL、并发限制和失败恢复 |
| P0 | 证据真实性被高估 | `auto_low_precision` 可发布；客户证据匹配包含宽松启发式 | 展示验证方式；高影响结论人工确认；建设标注评测集 |
| P0 | 备份和恢复不完整 | 正式 backup/restore 脚本未落地 | 备份 DB、WAL 一致性与文件；校验 manifest 并定期恢复演练 |
| P1 | 任务租约与结果写入原子性需增强 | 市场管线先写证据再执行租约保护的任务提交；客户任务缺少租约令牌/来源版本栅栏 | 给所有结果写入加租约/来源版本校验，补租约丢失和并发更新测试 |
| P1 | 客户事实冲突和状态语义不完整 | 当前事实按处理写入顺序切换，状态主要由固定事件规则计算 | 增加生效时间、冲突记录和人工覆盖审计；验证历史补录、丢单重启、暂停恢复等场景 |
| P1 | 测试命令可能空通过 | 多个递归测试脚本未绑定实际子包测试，回放仍占位 | 统一验证入口；空测试失败；补浏览器 E2E 与真实模型 opt-in 回归 |
| P1 | 观测字段不能完整代表真实成本 | 部分 Token/延迟为估算或常量，三个服务日志不一致 | 统一 usage、耗时、成本、Trace 与敏感信息脱敏 |
| P1 | 敏感客户材料送入外部模型 | 材料、模型调用、文件和本地对话历史均有数据治理要求 | 增加授权提示、字段脱敏、保留/删除策略和模型供应商数据政策检查 |
| P2 | 展示前端依赖运行时 CDN/Babel | 断网受影响，生产性能与供应链控制有限 | 改为预构建，锁定并本地托管依赖，增加 CSP |
| P2 | 多应用技术栈与身份割裂 | React/Next/Zod/Pi 版本、包管理、客户 ID 不统一 | 先共享 DTO、身份及设计规范，再按收益统一框架 |

“任务租约与结果写入”项为源码顺序暴露的架构风险，本次没有进行故障注入或线上复现，不应表述为已证实发生的数据事故。

## 十、建议演进路线

### 阶段一：建立受控内部试用基线

目标：先确保数据和任务可靠，再扩大用户范围。

- 统一认证、资源权限、密钥管理与接口限流。
- 持久化商机运行及报告，增加任务恢复和并发配额。
- 落实数据库/文件备份恢复与基础进程监控。
- 所有结果显式区分 Demo、规则、LLM、人工核验和低精度自动核验。
- 修复占位验收命令，建立可重复的 CI 验证入口。

### 阶段二：打通业务移交

目标：实现“市场发现 → 商机研究 → 人工确认 → 客户经营”。

- 建立统一国家编码、组织/品牌/客户 ID 及别名映射。
- 定义移交 DTO、幂等规则和来源血缘。
- 增加人工确认及回退机制，不自动将研究推断写成已确认客户事实。
- 统一证据展示、状态标签和报告版本。

### 阶段三：建立质量与容量门槛

目标：用数据判断系统是否具备扩大部署的条件。

- 建立事实抽取、引用支持度、国家范围/年份/业态正确率评测集。
- 对不同模型记录有效产出率、平均/P95 时延、修复轮次与单任务成本。
- 建立来源过期提醒和增量更新。
- 按实测瓶颈演进检索、数据库、对象存储和队列，而非直接全面重构。

推荐质量指标：

| 方向 | 指标 |
|---|---|
| 事实质量 | 抽取准确率/召回率、冲突率、错误客户归属率 |
| 证据质量 | 引文真实匹配率、结论支持率、时效有效率、人工通过率 |
| 评分质量 | 输入可追溯率、版本重放一致性、覆盖率及 EQI 分布 |
| Agent 效果 | 首轮提交成功率、平均修复轮数、工具失败率 |
| 工程运行 | 任务完成率、P50/P95 耗时、重试率、卡住任务数 |
| 成本 | 实际输入/输出 Token、单成功任务成本、搜索调用量 |
| 业务结果 | 移交采纳率、人工修订率、材料整理时间节省 |

## 十一、结论

本项目已形成三类有实际代码和测试支撑的能力：

- **以证据和确定性引擎支撑市场排序；**
- **以受控 Agent 综合国家及客户研究材料；**
- **以事件、事实和状态计算沉淀客户经营知识。**

现阶段的重点不应是继续叠加更多 Agent，而应优先完成 **鉴权、持久化、证据质量治理、可靠任务提交和跨模块移交**。这些基础完成后，现有 TypeScript 和受限工具架构足以支撑下一阶段业务验证；是否引入向量检索、分布式队列或服务拆分，应由实测需求决定。
